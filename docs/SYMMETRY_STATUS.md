## 2. 本轮的三处改动（都在 reference_impl，逐条有实测）

### 2.1 `MapGenHills.cpp` `MergeSlopeBlocks`：镜像格写错了格子 ✗→✓

成对盖章那一段原来**写死转置**：

```cpp
MapCell* m = CellAt((int16_t)(y + kOffY[k]), (int16_t)(x + kOffX[k]));   // ✗ 这是 LR 的镜像
```

左右对称的镜像是转置，上下对称是反对角翻转 `(x,y)->(k-y,k-x)`。于是 TB 上那 4 格的
`0xFFFF` 抹除与 `Level+1` 全落到了**别的格子**上。改成 `mg::MirrorCell`（LR 下两者恒等，
行为不变）。实测（`--diag-hills`）：

```
MergeSlopeBlocks 前后   改前 levelBad 71→175、markerBad 71→116
                        改后 levelBad 71→ 71、markerBad 71→ 71
整图纯黑                352287 → 329232（这一步没有把黑块清掉，见 2.2）
```

### 2.2 `MapGenHills.cpp` `FinalizeElevationSlopes`：TB 不做成对判定 ✓

`kKindOk` 原来把 TB 也算成"同类反射、可以成对"（LR 与 TB 共用一条成对路径）。**这条对 TB
不成立**，理由是几何的：

* 角块（2x2 格点）与格不是同一张格子。LR 是转置 `(x,y)->(y,x)`，块映到块的**同一锚点**；
  TB 是反对角翻转，块映到的是 `(k-y-1,k-x-1)` 那个块的锚点 —— **差一格**（块跨 `x..x+1`，
  而反射中心落在格点上）。所以"把权威格的角模式置换一下写给镜像格"给出的坡向与镜像格
  自己的角块对不上。

实测（`--stop-after hills: FinalizeElevationSlopes` 之后整图渲染；纯黑像素 / ≥150px 黑块 / 可见区族别不一致）：

| 做法 | black | blocks | vis |
|---|---|---|---|
| 成对，用 `kSlopeCornerMirror180` | 305976 | 1194 | 122 |
| 成对，改用左右那张转置表 | 465028 | 638 | — |
| **独立判定（现在这条）** | **474** | **0** | 236 |

整图（完整管线）：329232 / 1089 → **63406 / 28**。
上一轮把 TB 归进成对路径的依据是"族内一致率 51.8% → 49.8%"——那个指标对"片错但同族"
不敏感，换成渲染纯黑块后结论是反的。

### 2.4 `MapGenSymmetry.cpp`：海岸回来了（原来上下对称没有海岸）✗→✓

上一轮给 TB 走的是"**岛屿做法**"：把整张图的 **712 格岸件全换成普通地面**。日志一眼可见：

```

```

代价是整张图**没有海岸**——湖岸只剩"水对沙"的硬锯齿，玩家一眼能看出来。当轮的理由是"这套
tileset 没有按反对角翻转画的岸片美术"；重新实测后作废：

* 岸族的**足印**闭合度和左右对称完全一样（都是 40/42，缺的同样是 slot 41/42）；引擎自己的
  `MirrorTile` 在这张图上把 360 片全部配到了精确对应件（0 片走"最近件"回退）；
* 只取消抹除（沿用复制过来的岸件）更差：镜像半场一片黑阶梯（黑 55304 → 64611）；

所以现在 TB 与 LR 共用那条重选路径，`coast-island` 整段删除（源码里留注释说明"不要再加回来"）。

**岸件的"半片"及其收尾修补**（这是本轮最后一件）：

* "两半各判各的"会在镜像半场留下 **34 个半片**：2×2 的片只落了 1~2 格，渲染出来就是水里
  漂着的**浅色半方块**。成因是一趟顺序盖章里，后盖的 2×2 片把先盖的足印吃掉一两格（同一趟
  里同族片允许覆盖是引擎自己的判定）。检测器：`python3 build/ro-sym/shore_bad.py <图.yrm>`

  镜像）造成的。做法：检出半片 → 把它**整片**还原成卸妆前那一份（`shoreBackup_` 里存着）。
  整片还原后必然是完整实例（"只复制不重选"那一版实测 0 个半片）。实测：**44 个半片格 →
  还原 88 格 → 写出来 0 个半片**，黑像素总数不变（62245，0.565%）。
* **是否改好看了要用户拍板**：那 34 处从"浅色半方块"变成了"黑阶梯"（黑像素总数不变，是
  挪了位置）。另外两条试过并否决：足印冲突就不盖（半片 34→**61**，更差）；只还原破损那几格

闸门：`verify_symmetry.py` 的岸件一致性（实例的子帧集合要等于该片足印）现在也管 TB，
floor 0.95 —— 实测 **177/177（100%）**；"两半各判各的"那一版会被它判死。

**为什么"把海拔弄成一样"在 TB 上必然伤图（本轮的关键认识）**

`FinalizeElevationSlopes` 的高度来自 **2×2 角块**的最小角点（`cell->Level = lowest / 15`，1166 行）。
- 左右对称是**转置**：角块映到**同一个角块** ✓ → 两半读同一组角点 → 高度天然一致（实测 0）。
- 上下对称是**反对角翻转**：角块映到 `φ(角块) − (1,1)`，**差一格**。也就是说，一对镜像格
  读到的是**两块不同的地块** —— 它们的地板高度**本来就该不同**。把其中一个强行改成另一个的值，
  等于让某一格的高度与它**自己那块地**的角点不符 → 坡面/崖面美术立刻盖不住 → 黑。
  （实测三组数字正是这个：海拔越"对称"，黑越大。）

所以这不是"某一步没做对"，而是**"以 2×2 角块为单位的高程"这套算法在反对角反射下没有格点级
的不动结构**。要做到格点级严格对称，只能改角块格点本身的定义（层级极深的改动），或者在
**生成阶段就让两半共用同一套角块数据**——那是"半张图生成"级别的重构，本项目早先已把
"整半场抄"列为否决项（末尾抄实测 2.9% 黑）。

**因此目标需要重新界定**（下一轮开始前和用户确认）：把"levelBad → 接近 0"改列为**结构性
不可达**并记录在案；真正可交付的是"**看得见的黑块 = 0**"（现在 2 处 / 2865 步 = 0.07%）
—— 走**定点修补**：在 `RepairCliffPieces` 之后，对"正交邻居高 ≥2 层且本格是平地片"的格子，
按镜像成对补上崖件（只碰这类格子，不搬家、不改高度）。

**第 3 轮（新目标轮 1）实测：定点补美术也不行 → 那 2 处黑是结构性代价**

| TB 上做法 | 未覆盖落差 | 纯黑 |
|---|---|---|
| 基线 | **2**/2865 | **84565（0.768%）** |
| ① 成对比较"有没有落差美术"，缺的一侧从有的一侧镜像补片（263 格） | 9 ✗ | 137417（1.248%）✗ |
| ② ①＋"缺的那一侧必须真的有台阶"（181 格） | 8 ✗ | 109638（0.996%）✗ |

两条都撤回，基线逐字节恢复。

原因：**两半的局部几何本来就不同**（角块错位一格）。权威侧那一格盖得住自己的台阶的片，搬到
镜像侧那格**盖不住它的台阶**——台阶的位置/朝向不同。所以"补美术"和"配高度"一样，都是拿另一半
的答案去套另一半的问题。

**累计（第 1、2 轮 + 本轮）共 7 组变体全部实测更差**：整格抄（海拔+美术）、只抄海拔、丘陵末尾
整格抄、网格镜像、末尾配高度、补落差美术×2。规律一致：**海拔越"对称"、黑越大**。

**结论（写进目标记录）**：TB 的"2 处未覆盖落差 / 0.768% 黑"不是修得不彻底，而是**结构性代价**
——它和那 7.79% 的海拔差是同一个来源（`2×2` 角块与反对角反射不同构）。当前状态已经是所
有已测量方案里最优的一档。要再往下走只有两条路，都超出"修补"范畴：

* 改角块格点的定义（让高程算法在反对角反射下有格点级不动结构）；
* 或者生成阶段就让两半共用同一套角块数据（"半张图生成"级重构，且要重做崖/坡/岸的选片）。

仍有价值、且属于"修补"范畴的是目标③（崖/坡件在镜像半场摆对）：本轮把崖件朝向表推到了
**44/66 个 (片号,子帧) 组合可干净确定朝向**（≥80% 一致、n≥5），斜坡族那张表已经完整
（base 33：SE/SW/NW/NE = ReflectSlope 1↔3/2↔4）。下一轮可以把它补成完整的**方向表**接进
`MirrorTile`，让镜像半场的崖/坡件按朝向选片——这是唯一还没试过、且不与"改高度"纠缠的手段。

**第 4 轮（新目标轮 2）实测：把目标③量成了可验收的口径，并找到机制**

新增口径：**"两侧都是崖族的镜像对里，墙朝向不是对方镜像的比例"**（朝向 = 该格的 8 邻域里

| | 两侧都是崖族的镜像对 | 朝向不匹配 |
|---|---|---|
| **上下 TB** | 127 对 | **86 对（67.7%）** ✗✗ |

```

TB : 1 → 1    21 → 21   38 → 38   39 → 39                        ← 自己配自己，朝向错

TB 的通用候选搜索按**足印**匹配，撞上"足印在反对角翻转下自对称"的片就选了它自己；可是
**足印自对称 ≠ 美术自对称** —— 对手件（21 之于 1）才是画给那个朝向的。这与岸族当年的教训
一模一样（`kShoreWaterProfile` + 180 剖面置换就是为此而建）。

**修法**（下一轮落实）：给崖族加一张**逐片朝向剖面表**（同 `kShoreWaterProfile` 的做法）：
剖面可由生成图推出（本轮已能干净定出 44/66 个 (片号,子帧) 组合的朝向，≥80% 一致、n≥5），
`MirrorTile` 的崖族分支改成"同足印候选里挑剖面等于**镜像后剖面**的那一片"，而不是第一个。
只对 TB 生效（LR/180 逐字节不变）。验收口径就用上表那两行（目标：TB 从 86/127 降到个位数，
且黑 ≤84565、落差 ≤2）。

**第 5 轮（新目标轮 3）实测：崖族"对手件"的两条纯数据推导路线都不成立**

要修③（TB 崖件朝向错 67.7%），就得知道"哪一片才是画给反对角朝向的对手件"。本轮试了两条

**剩下的唯一可靠来源是美术本身**（象素级）：把源片的 TMP 按镜像变换后与同足印各候选片的
TMP 比对，取最像的那一片——这正是本项目当年为岸族建表时走过的路（"按片实例外围水向统计"
那一步是数据驱动，而对手件的认定最终是靠美术）。下一轮按这条做：先从 `build/oracle_assets`

**第 7 轮（新目标轮 5）实测：更正上一轮的口径 —— 真实朝向缺陷是 13.3%，不是 67.7%**

第 4/5 轮报的"崖件朝向不匹配 67.7%"是**被地形混淆**的：那个口径比的是"低侧方向位集"，
而位集是**地形属性**；TB 两半地形本来就不同（结构性海拔差），位集不同**未必**是美术摆错 ✗。
收紧到"**局部地形本身对称**的镜像对"（8 邻域高度模式互为镜像 —— 只有这些对里朝向不一致才
算美术缺陷）：

| 模式 | 地形局部对称的对 | 其中朝向不匹配 | 地形不对称的对（结构性） |
|---|---|---|---|
| 左右 LR | 235 | **0（0.0%）** ✓ | 0 |
| 180 | 72 | **7（9.7%）** | 16 |
| **上下 TB** | 45 | **6（13.3%）** | **82（65%）** |

结论修正为：
* 真实的崖件朝向缺陷是 **TB 6/45（13.3%）、180 7/72（9.7%）、LR 0** —— 量级小得多；
* TB 那 82/127（65%）"地形不对称"的对，就是同一个结构性海拔差在崖件这一层的投影 ✗，
  不是美术问题（也因此不可能靠换片修好）。

**③ 的验收口径改成这一行**（更严、且不混淆）：TB `6/45 → 0`、180 `7/72 → 0`，LR 保持 0。
修法仍是"按美术象素推对手件"（TMP 解码）；对手件一旦正确，这 6+7 格就会各自选到画给
自己朝向的那片。

**第 8 轮（新目标轮 6）实测：TMP 格式已探明一半，解码器是 1~2 小时的活**

为了让"按朝向挑对手件"（目标③）有数据来源，本轮开始探崖片 TMP 的格式。已确认（实测
`build/oracle_assets/Tile资源/温和/Cliff01.tem`，14456 字节）：

```
偏移 0x00  uint32 cx = 2          // 块的列数
偏移 0x04  uint32 cy = 3          // 块的行数
偏移 0x08  uint32 cblocks = 60
偏移 0x0C  uint32 w = 30          // 单块像素尺寸
偏移 0x10  uint32 h = 40
偏移 0x14  uint32 offs[cx*cy]     // 相对"数据区"(= 0x14 + cx*cy*4) 的块偏移；0 = 该块不存在
           block: uint32 x, uint32 y, uint32 extra_off, 然后是该块的象素数据
```
* 块 0 在 44 字节处（`offs[0]=0`），块 1 在 44+0x9D4、块 2 在 44+0x1C68、块 4 在 44+0x2A70；
* **块大小不一致**（相邻差 2516 / 4756 / 3576 字节），而 `12 + w*h + w*h*3 = 4812` ✗ —— 说明
  块内除 24 位图之外还有**变长的 extra/z 段**（`extra_off` 指的位置），格式比通常记的复杂。

所以象素路线要先把这块 extra 段的长度规则试出来（用"解码后象素是否合理、各块是否恰好
首尾相接"来自校验）。**这是一小时到两小时的活**，本轮预算不够，如实记录停在这里。

**给用户的两个选项**（下轮开工前定）：

2. 或者你直接给美术上的对应关系（当年岸族 #4↔#20 就是这样定的）——40 片崖的对手件，我立刻落表、
   接进 `MirrorTile`（只对 180/TB 生效），验收口径用第 7 轮那张表（TB 6/45 → 0、180 7/72 → 0）。

**第 9 轮（新目标轮 7）实测：TMP 块内不是纯 24 位图（差 20 字节 / 3580 不被 3 整除）**

本轮把上一轮的探针做成了可复用的自校验工具 `tools/tmp_probe.py`（它自己就抓出了我一个错：
偏移是**绝对文件偏移**，不是相对数据区）。用 `Cliff01.tem`（14456 字节）实测：

```
偏移表 = [0, 0x9d4, 0x1c68, 0, 0x2a70, 0]        （绝对文件偏移；0 = 该块不存在）
块1 @2516 : x=-30 y=15 extra_off=0x73c  实测大小 4756
块2 @7272 : x=0   y=30 extra_off=0x73c  实测大小 3592
块4 @10864: x=-30 y=45 extra_off=0x73c  实测大小 3592
```

判据与结论：
* `12 + w*h*3 = 3612` 与实测 3592 **差 20 字节**；`(3592-12)/3 = 1193.33` **不是整数** ✗
  → 块内**不是纯 24 位图**（有内部结构或压缩）；
* 三块的 `extra_off` 恒为 `0x73c` → 它不是"逐块的额外数据偏移"（不能按每块自己的 extra 段算长度）；
* 块 1 比另两块大 1164 字节 → 各块内容长度**不同**，进一步支持"压缩/变长段"。

所以"解 TMP 取美术"仍是一个要专门做的逆向小项目（估 1~2 小时，探针已经把它变成可自校验的
迭代）。**下一轮若没有用户给的对应关系，我就继续攻这个格式**；若能拿到对应关系，就直接落表接线。

**第 10 轮（新目标轮 8）实测：TMP 块内结构基本看出来了 —— 象素在块内 +37 处、明文 24 位**

在上一轮基础上把块内结构读出来了（`tools/tmp_probe.py` 已扩成直接打印这些字段）：

```
块2 @7272（共 3592 字节）
  12 字节头 : x=0, y=30, extra_off=0x73C
  子头 6×int32 = (952, 2722, 0, 15, 30, 29)          ← 语义待定（像"额外图偏移/大小"）
  首个 0xCDCDCD 在块内 +37 → 子头 25 字节，之后是**明文 24 位象素**
     (3592-37) = 3555 字节 = 1185.0 象素  ← 整数 ✔
块1 @2516（共 4756 字节）
  子头 = (952, 3304, -3, -15, 33, 44)；首个 0xCDCDCD 也在 +37
     (4756-37) = 4719 = 1573.0 象素       ← 整数 ✔
```

确定的：
* **透明色是 `0xCDCDCD`**（RA2 TMP 的经典标记）✔；
* 象素是**明文 24 位**、紧跟在**块内 25 字节子头**之后（即 12+25=37）✔；
* 各块的象素数不同（1185 / 1573）且**都不是 30×40=1200** ✗ → 块内存的不是"整块图"，
  很可能含"额外/受损图"（子头里的第二个 int 3304 / 2722 可能就是它的偏移或大小）。

仍待定：子头 6 个 int32 的确切语义 + 1185/1573 这两个数怎么来的。下一轮把它定完，就能解出
40 片崖的象素 → 逐候选比对 → `kCliffMirrorPartner[40]` → 接进 `MirrorTile`（只对 180/TB）。

**第 11 轮（新目标轮 9）突破：TMP 格式拿下（权威规格 + 字节级逐字段对上）**

来源：ModEnc 的 TMP 页（2025-05 修订，"File Format"）+ XCC 作者 Olaf van der Spek 的
`TMP_TS_Format.html`（GPL，图形编码部分）。两者合起来是完整规格：

```
FileHeader : uint BlockWidth, BlockHeight, BlockImageWidth, BlockImageHeight   // 16 字节
Index      : BlockWidth*BlockHeight 个 uint（绝对文件偏移；0 = 该格不存在）
CellHeader : int X, Y; uint ExtraDataOffset, ZDataoffset, ExtraZDataoffset;
             int ExtraX, ExtraY; uint ExtraWidth, ExtraHeight;
             uchar Bitfield; BYTE pad[3]; uchar Height, LandType, SlopeType;
             RGB TL, RGB BR; BYTE pad2[3];                                     // 52 字节
图形        : 紧跟 CellHeader 之后 —— **8 位**（不是 24 位）：
             正常图 = 等距形状的字节数（48x24 → 576；RA2 的 60x30 → 860/900，下一轮用
             ZDataoffset 反推定死），随后同样大小的一块 Z 数据，
             再后是 Extra 图（Rect，cx_extra*cy_extra 字节，0 表示透明）。
Bitfield    : 低 3 位 = HasExtraData / HasZData / HasDamagedData；文档原话举的例子就是 **0xCB**
              （`xxxxx011`）—— 正是我在文件里读到的那个字节。
```

**字节级验证**（`tools/tmp_probe.py` 已按此结构重写，实测 `Cliff01.tem`）：

```
BlockWidth=2 BlockHeight=3 BlockImage=60x30   指针表 = [0x28, 0, 0x9d4, 0x1c68, 0, 0x2a70]
格0 @40 : X=0 Y=0   Extra=(off 1852, 1,1 24x13)  Z=952 ExtraZ=2164  Bitfield=0xCB Height=4
          LandType=15 (**Cliff**) Slope=0 TL=(113,82,46) BR=(119,100,52)  pad=cd cd cd
格2 @2516 / 格3 @7272 / 格5 @10864 同样字段全对得上（4/6 格存在）
```

之前所有失败的根源找到了：**文件头是 4 个 int（16 字节），我当成 5 个** → 偏移全错位一格；
以及**图形是 8 位等距形状 + 一块 Z 数据**，不是明文 24 位（我据此做的两次编码假设自然全错）。

**下一轮**：按 ZDataoffset 反推 RA2 正常图形块的确切字节数 → 写解码器（8 位 → 用剧场调色板
转 RGB）→ 对 40 片崖做镜像变换、与同足印候选比象素 → 生成 `kCliffMirrorPartner[40]` →
接进 `MirrorTile`（只对 180/TB 生效）→ 验收 `TB 6/45 → 0`、`180 7/72 → 0`。

**第 12 轮（新目标轮 10）实测：布局互证通过，剩"象素纹理的行形状"一步**

用文件自身互证布局（比任何猜测都硬）：

```
格0 CellHeader @40（52 字节）→ 正常图 92..951
  长度 = ZDataoffset(952) - 92 = **860 字节**   ← 8 位 → 860 象素（60x30 等距形状）
Extra 图区紧密排列：格0 extra 起点 1852、尺寸 24x13 → 1852 + 312 = **2164 = 格0 的 ExtraZ** ✔
                   其余格的 ExtraZ（3304 / 2722）同样能由"前一块 extra 的起点+尺寸"推出 ✔

→ 布局（头 / 索引 / 52 字节 CellHeader / 正常图 / Z / Extra 图 / ExtraZ）**全部自洽** ✔。

**仍差一步**：正常图的 860 象素如何按行铺开（等距形状）。我按 TS 文档的比例（48x24 → 4..48..4

**新目标（30 轮窗口）开工：TMP 行形状只剩两条候选，且都不像完整菱形 → 需要"视觉参照"**

本轮（新目标第 1 轮的准备）实测：

* 正常图 = 块内 92..951 的 **860 字节**（由 `ZDataoffset − 92` 反推，已互证）；
* 860 字节里**没有主导的透明索引**（众数 150 只占 3.1%）→ 说明行内的象素基本都是不透明的，
  透明性由**行形状本身**表达（不在行内）✓，我原先"两端应当是透明索引"的检验因此无意义 ✗；
* 枚举"先增后减、步长 4、行宽 4..60、总和 860"的形状，**恰好 2 条候选**（都是 25 行）：
  `4,8,…,60,56,…,20` 与 `20,24,…,60,56,…,4`。两条都不闭合（首/末行不是 4 与 4）✗ ——
  而完整对称菱形（60x30）应当是 900 象素 ✗ → 所以 RA2 崖格的正常图**不是完整菱形**。

结论：**行几何不能靠算术猜**，要用"视觉参照"来定：本项目**已经有渲染器**，可以把一张现成

一次就能判定。这是下一轮的第一步（不再猜、直接看）。

**新目标轮 1 实测：想用"渲染里裁一个崖格"来裁定行形状，撞到两个实际障碍**

做法：在 `.yrm` 里找崖族格 → 用 `verify_symmetry` 同一套投影算出屏幕坐标 → 裁 60x30

结果（`sym3_t0_l3`，TB 温带内陆）：

  **裁剪区域完全落在渲染图之外**（0x0）✗；

实测（内陆 size2 2人 seed 20260913）：

| | 水/陆不一致 | 岸对（平移复制/足印镜像/无对应件） | 岸实例自洽 | 族别不一致 | 纯黑 |
|---|---|---|---|---|---|
| `2`（x 半边） | 0/13913 | 0 / 270 / 0 | 116/127 | 16.4% | 43158（0.392%） |
| `4`（y 半边） | 0/13913 | 0 / 485 / 0 | 208/224 | 12.5% | 50200（0.456%） |

**镜像半场没有湖岸**（用户实测，第二轮修）：`MirrorTile` 开头那道 kind 白名单里没有新模式
（`kind != LR && kind != Rotational180 && kind != TB → return -1`），于是**每一片岸件一进来就
被判"无对应件"**，镜像半场那片湖只剩硬锯齿边、没有绿色湖岸裙边。日志一眼可见：

```
rotational-180      copied 6956 cell pairs whole, 270 art pieces turned (262 片岸件)
rotational-180-alt  copied 6956 cell pairs whole,   0 art pieces turned (  0 片岸件)   ← 修前
rotational-180-alt  copied 6956 cell pairs whole, 485 art pieces turned (459 片岸件)   ← 修后
```

修法就是把那道白名单改成 `!mg::IsRotation180(kind)`（180 本来就在名单里，所以等价于没变）。
这类"白名单写死名字"的地方共 8 处，现在全部走 `IsRotation180` / `AuthoritativeXY`。

**收尾修补换人**：TB 那 44 处"半片"我先写过一版"把整片还原成卸妆前那一份"的补丁——它能
把半片清零，但**黑块只是挪了位置**（那几处从浅色半片变成黑阶梯），而且它会把一件的**全部**
格子还原，牵连到没坏的格。用户在家里那版（`109b137`）是**根治**：只给"盖章中途 `return false`
留下的占位格"补上（只写占位格、不覆盖任何已有美术），已在本次融合中替换掉我那版。实测两种
做法对**本机参数下的 TB** 都是 0 处（TB 走左右那条路之后已经不留占位缺口），而新模式实测有
4 件 5~8 格被这版补上。

**试过并否决：把 TB 的"成对盖章"扩到 180 一族**（`PlaceCliffs` 第二趟的 `cpaired`）。动机是
两处未覆盖落差都在**复制侧的崖面片**上（复制侧那格的美术没盖住落差，权威侧盖住了 → 说明
`MirrorTile` 取不到对应件时被原样照搬）。实测**两个口味都变差**，按规矩撤回：

| 判据 | 180 改前 → 改后 | 新模式 改前 → 改后 |
|---|---|---|
| 未覆盖落差 | 0/2189 → 0/2641 | 2/2942 → **9**/2801 |
| 纯黑像素 | 44174 → **55021** | 54238 → **77760** |
| ≥40px 黑块 | 589 → 518 | 545 → 533 |

机理和岸族那次不同：岸族那条路要走官方选片树（顺序依赖强，当时否决有道理），而这一趟只是
"权威格盖章、镜像格跟着盖同一片"，与两格距离无关——但它会把生成器自己选的那片**覆盖掉**。
剩下那 2 格的正确态度与源码里已有的记录一致（岸族 #4/#20）：**"取不到对应件"时宁可留一条
差异，也不要用一片朝向不对的件去填**。所以这两格作为已知残差记录在案，不再动。

**闸门为什么没抓住它**（教训）：岸对检查只比**足印**——2×2 的岸件不管朝向对不对，足印都是
2×2，所以"原样复制"也能测出"0 处平移复制"。现在 `check_rot180_flavours` 多读一条**本趟自己的
日志计数**，要求两种口味都必须 `art pieces turned > 0`（实测 270 / 485），0 就判死。

闸门：`verify_symmetry.py` 新增 `check_rot180_flavours`（13 项）——两种口味的轮廓必须
13913/13913 对称、岸对必须全是足印镜像、**地图里必须有水**（缝墙挡错轴的回归会被它抓住）、
两种口味必须给出**不同**的图、各自可复现。页面 `#symmetry` 现在把引擎实现的五种全部列出
（`0/1/3/2/4` + 随机），`verify_uicontract.py` 的钉死值同步更新。

### 2.5 诊断能力：`--stop-after hills:<Step>`

`mgconsole` 原来只有 `--diag-hills`（打印，不写盘）。现在 `--stop-after` 也接受
`hills:<Step>`（十个子步任一个），于是**每一步都能渲染**——"黑是哪一步画出来的"从推断
变成实测（`FinalizeElevationSlopes` 之前 474、之后 305976，一步定位）。
